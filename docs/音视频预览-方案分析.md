# 音视频预览：独立做，还是在本插件上完善？

> 分析对象：`dsh-file-agentero`（工作区文件快速预览）
> 运行环境：DSH Web GUI `0.2.2-rc.2`，右侧预览由 `@deepseek-ai/dsh-client-ui-sidebar-documentpreview` 提供
> 结论一句话：**不独立做。在现有插件里新增一个「媒体渲染器」即可，代码量约一个模块，不改 DSH 内核。**

> 状态：已按本方案落地到 0.2.0（`media.js` + `client.js` 的 `MediaBody`），实现与验收记录见 `CHANGELOG.md`。

---

## 1. 今天为什么打不开

右侧预览不是「不认识 mp4」，而是**认识但故意不渲染**：

- 预览包把 `mp4 / mov / mkv / webm / flv / wmv / m4v / mp3 / wav / flac / ogg / m4a / aac …` 列在 `UNVIEWABLE_BINARY_EXTENSIONS` 里（`document/unviewable.ts`）。
- 文件命中这份列表、且**没有任何渲染器注册该后缀**时，预览直接走「不支持的文件类型」空状态，只保留「用本机应用打开」的入口（`sidebar.right.tab.document.unpreviewable`）。
- 这就是你看到的「要借助外部软件」——外部打开是 DSH 的兜底，不是缺失的能力。

同时，预览包**本身就是为插件扩展设计的**：

- `ctx.documentPreviews.register({ id, extensions, binaryExtensions, priority, title, loading, wrap })`
- `priority: 'extension'` 默认值，**第三方实现优先于内置实现**
- `loading: 'renderer'` 表示「渲染器自己加载内容」——不读纯文本、不整文件读字节，**不受 32 MiB 整文件上限约束**
- 组件注册进 `sidebar.right.tab.document` 的 keyed 槽，`key` 就是上面那个 `id`

所以「音视频渲染」在架构上**不是新能力，只是少注册了一个渲染器**。

## 2. 三个选项的对比

| 维度 | A. 在本插件加（推荐） | B. 独立插件 | C. 改 DSH 内核 |
|---|---|---|---|
| 实现量 | 1 个渲染器 + 2 条 Host 路由 | 同一份代码，另起包 | 需要改 asar 内包，无法随插件分发 |
| 用户安装 | 已有插件直接升级 | 要再装一个包 | 不可能 |
| 与「跟随编辑」联动 | 天然一体：写盘后自动打开即播放 | 两个插件都装才有完整体验，少装一个就回到「不支持」 | — |
| 复用现有设施 | i18n、主题样式、版本更新页、安装说明全部复用 | 要重建一套 | — |
| 维护成本 | 一个版本号 | 两套发布/兼容矩阵 | 跟随 DSH 升级 |
| 何时该选它 | 默认 | 媒体能力要单独上架、或给不用 quicklook 的人 | 永远不 |

**判断依据**：这个功能的价值 100% 依附于「右侧预览」这个场景。独立成包不会让它更好用，只会让用户多装一步、让两个插件互相依赖。真正该独立的信号是**能力边界变化**：转码、字幕烧录、逐帧、时间线、AI 拉片——那时把代码抽成 `dsh-media-preview` 作为可选包即可。

**建议**：保持一个 bundle，新增 `media/` 模块；Host 侧新增两条路由；版本号升 `0.2.0`。若将来要拆，整目录 + 路由可直接搬走，因为接口只依赖 DSH 公共槽位。

## 3. 已验证的技术路径

### 3.1 客户端（浏览器半边）

```js
// 元数据：声明后缀与加载方式
ctx.documentPreviews.register({
  id: '@deepseek-ai/dsh-file-agentero/media',
  extensions: ['mp4', 'm4v', 'webm', 'ogv', 'ogg', 'mov', 'mp3', 'wav', 'm4a', 'aac', 'flac', 'opus'],
  binaryExtensions: [/* 与 extensions 相同：这些都是二进制容器 */],
  priority: 'extension',
  title: () => t('title'),
  loading: 'renderer',   // 关键：自己加载，不走整文件读取
  wrap: false,
})

// 组件：同一个 id 注册进 keyed 文档槽
ctx.slots.inject('sidebar.right.tab.document', () => ctx.slots.register(
  { name: 'sidebar.right.tab.document', key: MEDIA_BODY_ID, locale: NS },
  MediaBody,
))
```

渲染器模式下组件拿到的是 `content = { kind: 'renderer', revision, loaded(version), failed(), reload() }`，由组件决定怎么加载；`<video>/<audio>` 直接指向 Host 的流式路由，浏览器自己发 Range 请求。**不需要把文件读进 JS 内存**。

### 3.2 Host 半边

必须走**带鉴权的 Fetch 路由**，不能用现有的 `webServer.register`：

| 方案 | 鉴权 | `<video>` 能否用 | 结论 |
|---|---|---|---|
| `webServer.register`（现有 translate 路由用法） | 自己做（loopback + 自定义头） | ❌ 元素发请求不能加自定义头 | 需要额外自签 token，多一层 |
| `ctx.connection.fetch.register` | 复用 `/api` 的浏览器 cookie 鉴权与 Host/Origin 检查 | ✅ 同源请求自动带 cookie | **推荐** |
| `workspaceFiles.readBytes` 整文件 / Blob URL | 自带 | ✅ | ❌ 32 MiB 上限、无 seek、大文件直接拖死内存 |

路由契约：

```
GET/HEAD /api/file-agentero/media?sessionId=…&path=…
  Range: bytes=0-          → 206 + Content-Range + Accept-Ranges: bytes
  无 Range                 → 200
  越界/畸形                → 416 + Content-Range: bytes */<size>
  HEAD                     → 200 + Content-Length（浏览器探测用）

GET /api/file-agentero/media-stat?sessionId=…&path=…
  → { size, version, type }（元信息行、变更检测）
```

要点：

- 文件权限**复用平台已有的权威**：`ctx.sessions.get(id)?.header.cwd ?? ctx.sandboxPolicy.workspaceRoot` 得到 workspace scope，再调 `ctx.workspaceFiles.stat/readBytes(scope, path, { range })`。不新增文件访问面。
- `readBytes` 单窗口受 `maxBytes`（默认 2 MiB）约束，因此**每个响应最多回 2 MiB**，`Content-Range` 照实写；浏览器会自己续请求。想减少请求数可改成在一条响应内循环读多块（需处理背压），属于优化项。
- 后缀白名单 + 只读 + 禁止目录，路由不接受写方法。
- 路由挂在 `/api` 下，客户端拼 URL 时去掉前导 `/`、使用文档相对路径，兼容部署前缀。

### 3.3 接入清单

| 半边 | 现状 | 需要增加 |
|---|---|---|
| Host `index.js` | `inject = ['webServer']` | `connection`、`workspaceFiles`、`sessions`、`sandboxPolicy`（保留 `webServer`，翻译/更新路由不动） |
| Client `client.js` | `inject = ['slots', 'locale', 'sidebarRight']` | `documentPreviews`（预览包已在 `package.json` 的 `dsh.client.inject` 里声明，加载顺序有保障） |

均为增量，不删改现有注册；翻译路由仍走 `webServer.register`，媒体流单独走 `connection.fetch`，两者互不影响。

### 3.4 与现有功能的联动

- **跟随编辑**：Agent 写出 `render.mp4` → 现有逻辑自动在右侧打开 → 新渲染器直接接管播放。这是留在同一插件最强的理由。
- **文件更新**：自动刷新开启时，预览包在文件版本变化后会调 `content.reload()`（revision 变化）。播放器以 `key={revision}` 换源，并保留/提示两种策略二选一（建议：正在播放时提示「文件已更新」，暂停时静默换源）。
- **流式写入**：`write` 过程中的实时面板与媒体无关，写盘完成后的正式预览才走播放器，不必改动。
- **失败态**：`content.failed()` 让预览头部出现「重新加载」；同时保留「用外部应用打开」入口，兼容旧习惯。

### 3.5 自动播放

Chromium 禁止有声自动播放，因此默认 `muted + autoPlay`，播放器控制条一键开声，并在下方给一行提示。这是生态里同类插件的通用做法。

## 4. 格式矩阵（Chromium / Electron 桌面端）

| 后缀 | 容器/常见编码 | 预期 | 处理 |
|---|---|---|---|
| `.mp4` `.m4v` | H.264 + AAC | ✅ 最稳 | 播放 |
| `.webm` | VP8/VP9 + Opus | ✅ | 播放 |
| `.mov` | H.264/AAC 可播；ProRes 不行 | ⚠️ 看编码 | 播放，失败给可读文案 |
| `.ogv` `.ogg` | Theora/Vorbis、Opus | ⚠️ 视平台 | 播放 |
| `.mp3` `.wav` `.m4a` `.aac` `.flac` `.opus` | — | ✅ 基本可播 | 播放 |
| `.mkv` `.avi` `.wmv` `.flv` | Matroska / MPEG-4 Part 2 / WMV / FLV | ❌ 浏览器不解码 | 保持「不支持 + 外部打开」；可选转码预览（见阶段 3） |

**原则**：能播的才注册；不能播的后缀不要抢——抢了只会把「不支持」换成「黑屏」。

## 7. 风险与缓解

| 风险 | 说明 | 缓解 |
|---|---|---|
| 编解码不可控 | 同一后缀可能装 ProRes/HEVC，浏览器黑屏 | 失败态可读；文档给「H.264/AAC 最稳」；不预判能播 |
| 路由安全 | 新路由等于新的文件出口 | 复用 `/api` 鉴权；只读方法；后缀白名单；鉴权后仍做路径校验 |
| 内存/背压 | 大 range 一次读入 | 单块 ≤2–4 MiB；响应中断即 abort 上游读取 |
| 自动播放策略 | 有声自动播放被拦 | 默认静音 + 明确提示 |
| 文件被覆盖 | 播放中版本变化 | 用 stat 的 `version` 比对，提示后换源，不静默黑屏 |
| 与既有「打开方式」冲突 | 用户仍可能想用本机播放器 | 保留外部打开按钮，不独占入口 |
| 生态已有实现 | 功能不新，用户可能问「为什么不直接用现成的」 | 见下节；路线已被验证，差异化在「预览一体化」 |

## 8. 生态参照

npm 上已有两个同类插件，实现路线与本方案一致（`ctx.connection.fetch` + Range + workspace 文件权限），可以先装一个验证体验，再决定自研深度：

- [`@lvxianchao/dsh-video-preview`](https://www.npmjs.com/package/@lvxianchao/dsh-video-preview) 1.1.1（MIT）：约 220 行 Host + 330 行客户端，支持 206/416、muted autoplay、stat 元信息。
- [`@lifenrir/dsh-video-preview`](https://www.npmjs.com/package/@lifenrir/dsh-video-preview) 0.1.4（MIT）：`ctx.fs.readByteRange` 4 MiB 分块、HEAD 预检、主题变量跟随。

两者都只做视频、不做音频，也不带「跟随编辑 / 划词引用」的一体化——这正是本插件做完之后的差异点。若不想重写，也可以参考其路由实现（MIT，保留版权声明即可）。

## 9. 明确不做（本期）

- 不做独立播放器应用、不做媒体库/播放列表。
- 不做视频剪辑、抽帧导出、字幕编辑。
- 不给不支持的容器自动转码（放到 M3，且必须异步 + 缓存 + 可取消）。
- 不改 DSH 内核，不为媒体单独造鉴权体系。
